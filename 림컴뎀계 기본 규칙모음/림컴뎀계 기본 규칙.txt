지금까지의 작업을 종합하면, 우리가 만드는 것은 단순한 **“스킬 하나의 데미지를 계산하는 계산기”가 아니라, 림버스 컴퍼니의 실제 1턴 전투 규칙을 재현하는 상태 전이형 피해 분석 엔진**이야.

## 1. 최종 목표

사용자가 직접 지정한

* 인격
* 스킬
* 행동 순서
* 공격 대상
* 전투 시작 상태
* 자원
* 버프/디버프
* 상태이상
* 공명
* 각종 준비 상태

를 입력하면,

```text
START_STATE
   ↓
사용자 지정 행동
   ↓
Action Queue
   ↓
스킬/코인 처리
   ↓
조건 판정
   ↓
피해 계산
   ↓
상태 변화
   ↓
추가/강제/원호 공격
   ↓
Trigger
   ↓
다음 행동
   ↓
TURN END
   ↓
END_STATE
   ↓
STATE_DIFF
   ↓
NEXT_TURN_STATE
```

까지 계산하는 것이 최종 목표야. 

즉 **1턴을 완전히 계산하되, 다음 턴 전체를 자동 플레이하지 않는 것**이 핵심 범위다.

---

# 2. 우리가 만들지 않는 것

이건 꽤 중요해.

### 하지 않음

* AI의 행동 선택
* 최적 행동 자동 탐색
* 자동 전투 시뮬레이터
* 누가 전투에서 이기는지 자동 판단
* 무제한 다중턴 자동 진행
* 사용자가 지정하지 않은 행동의 임의 선택

사용자가

> A가 S3 → B가 S2 → C가 S1

이라고 지정하면 **그 행동을 계산하는 것**이 목적이다. 

다만 1턴 중에 기믹 때문에 원호공격이나 추가공격이 발생한다면 그것은 계산기가 자동으로 실행해야 한다.

---

# 3. 진짜 핵심은 `TurnState`

계산기의 중심은 데미지 공식 자체가 아니라 **현재 전투 상태**야.

```text
TurnState
├─ 아군
├─ 적
├─ HP / SP
├─ 공격/방어 레벨
├─ 자원
├─ 상태이상
├─ 버프/디버프
├─ 공명
├─ 특수 Flag
├─ Pending Effect
└─ 다음 턴 예열
```

그리고 각 행동이 이 상태를 변화시킨다.

그래서:

```text
스킬 A
→ 상태 변화
→ 스킬 B
→ 변경된 상태에서 다시 계산
```

이 되어야 한다. 

---

# 4. 행동은 `ActionQueue`로 처리

특히 우리가 최근 집중했던 부분이 여기야.

```text
사용자 지정 행동
        ↓
Resolved Action
        ↓
코인 처리
        ↓
Trigger 발생
        ↓
추가/원호/강제 공격 생성
        ↓
ActionQueue 삽입
        ↓
실행
```

예를 들어:

```text
A S3
 ↓
조건 충족
 ↓
원호 공격 발생
 ↓
원호 공격 실행
 ↓
B S2
```

처럼 **실제 전투에서 발생하는 행동 연쇄를 하나의 공통 시스템으로 처리**하려는 거야.

인격마다 `if identity == ...`를 계속 추가하는 방식은 최대한 피한다. 

---

# 5. 모든 기믹을 공통 Primitive로 표현

현재 우리가 아키텍처를 계속 다듬는 이유가 이것 때문이야.

기본적으로:

```text
Rule
├─ Trigger
├─ Condition
├─ Target
├─ Effect
├─ Timing
└─ Activation Limit
```

구조로 표현한다.

예:

> 호흡 7 이상이면 코인 위력 +1

을

```text
Condition
└─ poise >= 7

Effect
└─ coin_power +1
```

로 표현하는 식이다. 

그래서 새로운 인격이 추가되어도 가능한 한 **새 Python 코드를 만드는 것이 아니라 데이터와 기존 Runtime을 조합**하는 방향이다.

---

# 6. 현재 프로젝트에서 특히 중요한 범용 시스템

현재 우리가 구축해 온 핵심 축은 대략:

```text
Condition
Target
Effect
Trigger
ActionQueue
Resource
Skill Transform
Activation
Damage Modifier
RuleIR
TurnState
Event Log
```

이다.

특히 최근 작업의 방향은 **RuleIR → 공통 Runtime → 실제 전투 엔진**으로 이어지는 구조를 만드는 것.

RuleIR Compiler도 이미 만들었지만, 현재 단계에서는 **구조적 변환과 실제 실행 연결을 구분**해야 한다. 즉 RuleIR 변환율이 곧 전투 구현률은 아니다. 

---

# 7. 인격 데이터도 결국 선언형으로 만든다

최종적으로는 대략:

```text
수감자
└─ 인격
   ├─ S1
   │  ├─ 기본 정보
   │  ├─ Coin 1
   │  ├─ Coin 2
   │  └─ Effects
   ├─ S2
   ├─ S3
   ├─ 방어
   ├─ 패시브
   └─ 보조 패시브
```

각 규칙에는:

```text
natural_text
trigger
condition
target
effect
timing
activation_limit
rule_id
source
dependency
implementation_status
```

등을 붙여서 **원문과 실제 실행 규칙을 분리**한다. 

이렇게 해야 나중에

> "이 +3 피해는 어디서 나온 거지?"

를

```text
Damage
 ↓
Modifier
 ↓
Rule ID
 ↓
인격 / 스킬 / 코인
 ↓
원문
```

까지 추적할 수 있다.

---

# 8. 우리가 중요하게 보는 것은 "커버리지 숫자"보다 실제 규칙 재현성

최근 0.5.62 전체 감사에서:

* 184 인격
* 공격 스킬 621개
* 방어 스킬 212개
* 패시브 588개
* 완전 파싱 66 / 621
* 부분 파싱 499 / 621
* 미파싱 58 / 621

이 확인됐어. 

그런데 여기서 **10.6%를 전체 전투 구현률이라고 보면 안 된다.**

왜냐하면 하나의 스킬 안에서 일부 효과만 빠져도 `partial`이기 때문이야.

실제로 가장 큰 병목은:

```text
기본 Damage Formula
        ↓
        이미 상당히 구축됨
        ↓
스킬 설명
        ↓
Target
Condition
Resource
Trigger
Additional Action
Skill Transform
        ↓
여기가 병목
```

이라는 게 감사 결과에서 드러났다. 

그래서 최근 작업들이 **Target / Trigger / Action / Resource / Skill Transform / RuleIR** 쪽으로 계속 이동한 거야.

---

# 9. 7대 공통 키워드와 소속 기믹도 분리

현재 기본 공통 키워드는:

* 충전
* 출혈
* 호흡
* 진동
* 화상
* 파열
* 침잠

이고, 소속 기믹은 별도의 축으로 본다. 

즉:

```text
키워드
≠
소속
```

이다.

그리고 **생체 재료 같은 특정 명칭을 무조건 별도 Runtime으로 만드는 것도 피한다.** 기존 공통 자원/기믹으로 표현 가능한지 먼저 본다. 

---

# 10. 실제 게임 규칙을 임의로 일반화하지 않는다

이것도 최근 작업에서 확실히 굳어진 원칙이야.

예를 들어 실제 인격 데이터에:

> 특정 조건에서 진동/파열을 2배로 부여

가 있으면 **그 인격의 규칙으로 구현**한다.

그걸 보고 일반 `진동 Runtime = 2배` 같은 식으로 확대하면 안 된다. 실제 데이터에 존재하는 규칙과 공통 시스템의 규칙을 분리해야 한다. 

즉:

```text
실제 인격 원문
 ↓
규칙 분류
 ↓
공통 Runtime으로 표현 가능한가?
 ↓
가능 → 공통 Runtime
불가능 → 필요한 범위의 확장
```

순서다.

---

# 11. 거울던전/Gift는 범위에서 제외

현재 범위에서는:

**거울던전 / Gift를 계산기 대상에서 제외**한다.

따라서 Gift Runtime을 만들거나 Gift 데이터를 전투 엔진에 끌어들이지 않는다.

대신 **인격/E.G.O의 일반 전투 규칙**에 집중한다. 

---

# 12. 다중턴은 "자동 시뮬레이션"이 아니라 상태 연결

이 부분도 프로젝트 성격을 정확히 이해하려면 중요해.

1턴이 끝나면:

```text
TURN 1
START
 ↓
ACTION
 ↓
END
 ↓
STATE_DIFF
 ↓
NEXT_TURN_STATE
```

를 만든다.

그다음 사용자가

> 이 상태에서 2턴에는 B가 S3을 사용한다

라고 정하면:

```text
Turn1.NextTurnState
        ↓
Turn2.StartState
        ↓
사용자 지정 행동
```

으로 연결한다.

즉 **반자동 다중턴 분석은 가능하지만 풀 오토 전투 시뮬레이터는 아니다.** 

---

# 13. 그리고 결과를 "왜 이렇게 나왔는지" 설명할 수 있어야 한다

이게 우리가 일반적인 데미지 계산기보다 훨씬 크게 잡고 있는 부분이야.

각 계산은:

```text
START_STATE
ACTION_TRACE
END_STATE
STATE_DIFF
NEXT_TURN_STATE
```

를 남긴다.

그리고 Action Trace 안에는:

```text
스킬
→ Clash
→ Coin
→ Trigger
→ Modifier
→ Damage
→ 상태 변화
→ 자원 변화
→ 추가 행동
```

이 기록된다.

그러면:

```text
42,800
```

이라는 숫자만 보여주는 게 아니라,

> 왜 42,800이 되었는가?

를 역추적할 수 있다.

# 14. 현재 개발 방식의 원칙

우리가 정한 개발 원칙은 상당히 명확해.

### ① 전체 데이터는 한 번 분류 감사

184 인격을 매 작업마다 처음부터 다시 읽지 않는다.

### ② 관련 영역만 깊게 판다

예:

```text
거미집 기믹
→ 거미집 인격
→ 관련 Runtime
→ 공통 Runtime
```

만 본다.

### ③ 반복 기믹은 범용화

원호공격, 지원공격, 처치 보상, 조건부 추가공격 등은 공통 시스템으로 흡수한다.

### ④ 인격 전용 하드코딩은 최후의 수단

공통 Runtime으로 표현할 수 있으면 그렇게 한다.

### ⑤ 새로운 패턴은 억지로 기존 시스템에 끼워 넣지 않는다

반복 가능성이 있으면 새로운 Primitive/추상화를 만들고, 정말 일회성인 경우에만 전용 처리를 한다. 

---

# 15. 테스트도 "매번 전체"가 아니다

최근 정리한 방식대로:

```text
Primitive 수정
→ Primitive 테스트
→ 관련 회귀

Resource 수정
→ Resource 테스트
→ 관련 회귀

Target 수정
→ Target 테스트
→ 관련 회귀

RuleIR 수정
→ Compiler + 관련 Primitive

공통 Core/Runtime 변경
→ 전체 회귀

릴리즈
→ 전체 회귀
```

로 간다. 

즉 **개발 속도를 위해 영향 범위 기반 테스트**를 사용한다.

---

# 한 문장으로 압축하면

> **우리가 만드는 것은 “사용자가 지정한 1턴을 실제 림버스 전투 규칙에 따라 상태 전이·트리거·추가행동까지 재현하고, 최종 피해뿐 아니라 그 피해가 나온 과정과 다음 턴 예열 상태까지 추적할 수 있는 선언형 전투 엔진”이다.**

그리고 현재 가장 중요한 방향은 **새 인격을 하나씩 하드코딩하는 것이 아니라, 실제 인격 데이터에서 반복되는 규칙을 찾아 `Condition → Target → Effect → Trigger → Action`이라는 공통 언어로 흡수해서 실제 계산 가능 범위를 넓히는 것**이야.
