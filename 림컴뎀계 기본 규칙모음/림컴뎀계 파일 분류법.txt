ㅇㅇ. 파일이 많아질수록 **“어디에 뭐가 있는지 10초 안에 찾는 구조”**가 중요하니까, 파일 자체를 기능별로 분리하고 **번호 + 고정 접두사 + 검색용 인덱스**를 같이 두는 방식이 좋다.

# 파일 분류 방법론

## 1. 가장 먼저 6개의 큰 구역으로 나눈다

프로젝트 최상위 폴더를 이렇게 만든다.

```text
림버스컴퍼니_데미지계산기/
│
├─ 00_프로젝트/
├─ 01_게임데이터/
├─ 02_규칙/
├─ 03_전투엔진/
├─ 04_테스트/
├─ 05_문서/
└─ 06_도구_인덱스/
```

번호를 붙이는 이유는 **폴더가 많아져도 항상 같은 순서로 보이게 하기 위해서**다.

---

# 2. 00_프로젝트

프로젝트 자체를 관리하는 파일.

```text
00_프로젝트/
├─ PROJECT_OVERVIEW.md
├─ PROJECT_STATUS.md
├─ CHANGELOG.md
├─ TODO.md
├─ DECISION_LOG.md
└─ HANDOFF/
```

### 각각의 역할

**PROJECT_OVERVIEW**

> 우리가 뭘 만들고 있는가?

**PROJECT_STATUS**

> 현재 어디까지 만들었는가?

**CHANGELOG**

> 무엇이 언제 변경됐는가?

**TODO**

> 앞으로 무엇을 해야 하는가?

**DECISION_LOG**

> 왜 이렇게 만들기로 결정했는가?

**HANDOFF**

> 다음 AI에게 넘길 때 사용하는 자료.

---

# 3. 01_게임데이터

여기는 **게임에서 실제로 가져온 데이터**를 넣는다.

```text
01_게임데이터/
│
├─ identities/
│   ├─ yi_sang.json
│   ├─ faust.json
│   ├─ don_quixote.json
│   └─ ...
│
├─ ego/
│
├─ buffs_debuffs/
│
├─ keywords/
│
└─ raw/
```

여기서 중요한 건:

> **게임 원본 정보와 우리가 만든 계산 로직을 섞지 않는다.**

예를 들어:

```text
raw/
└─ 림버스컴퍼니_버프_디버프_원본.txt
```

은 원본 자료다.

반면:

```text
buffs_debuffs/
└─ bleed.json
```

은 원본을 정리해서 프로그램이 사용할 수 있게 만든 데이터다.

---

# 4. 인격 파일은 이름을 통일한다

인격 파일은 지금처럼 인격별로 흩어놓기보다 **수감자별 파일**을 유지하는 방향이 좋다.

예:

```text
identities/
├─ yi_sang.json
├─ faust.json
├─ don_quixote.json
├─ ryoshu.json
├─ meursault.json
├─ hong_lu.json
├─ heathcliff.json
├─ ishmael.json
├─ rodion.json
├─ sinclair.json
├─ outis.json
└─ gregor.json
```

찾을 때:

> “료슈 자료 어디 있지?”

→ `ryoshu.json`

로 바로 찾을 수 있다.

---

# 5. 02_규칙

여기가 **게임 규칙을 모아놓는 곳**이다.

```text
02_규칙/
│
├─ damage/
├─ coin/
├─ clash/
├─ status/
├─ resource/
├─ condition/
├─ target/
├─ trigger/
├─ action/
└─ turn/
```

예를 들어 데미지 계산을 찾고 싶으면:

```text
02_규칙/damage/
```

클래시 규칙이면:

```text
02_규칙/clash/
```

출혈·화상·진동 같은 상태이상이면:

```text
02_규칙/status/
```

이렇게 바로 들어갈 수 있다.

---

# 6. 03_전투엔진

실제로 규칙을 **실행하는 코드**다.

```text
03_전투엔진/
│
├─ state/
├─ action/
├─ queue/
├─ condition/
├─ effect/
├─ trigger/
├─ damage/
├─ resource/
├─ status/
├─ target/
├─ solver/
└─ runtime/
```

여기서 중요한 구분:

```text
02_규칙
= 게임 규칙이 무엇인가?

03_전투엔진
= 그 규칙을 프로그램이 어떻게 실행하는가?
```

예:

```text
02_규칙/status/bleed.md
```

에는

> 출혈이 어떤 규칙으로 작동하는가?

가 들어가고,

```text
03_전투엔진/status/bleed_runtime.py
```

에는

> 그 규칙을 실제 계산기에 어떻게 적용하는가?

가 들어간다.

---

# 7. 04_테스트

테스트도 아무렇게나 모으지 않는다.

```text
04_테스트/
│
├─ unit/
├─ integration/
├─ regression/
├─ identity/
├─ skill/
├─ status/
├─ damage/
├─ trigger/
└─ fixtures/
```

### Unit

작은 기능 하나만 테스트.

```text
출혈 +1이 제대로 되는가?
```

### Integration

여러 기능이 같이 작동하는지 테스트.

```text
출혈 → 조건 충족 → 추가 피해
```

### Regression

기존에 되던 것이 새로운 수정 때문에 망가지지 않았는지 확인.

### Identity

특정 인격 테스트.

### Skill

특정 스킬 테스트.

### Fixtures

테스트에 사용하는 고정된 전투 상황.

---

# 8. 05_문서

사람이 읽기 위한 자료는 여기로 모은다.

```text
05_문서/
│
├─ 게임규칙/
├─ 개발방법론/
├─ 구현현황/
├─ 작업기록/
├─ 검증기록/
└─ 인수인계/
```

예를 들어 지금 우리가 만든 문서는:

```text
05_문서/개발방법론/개발_방법론.md
```

이런 식이다.

---

# 9. 06_도구_인덱스

이 부분이 **“찾기 쉽게”의 핵심**이다.

```text
06_도구_인덱스/
│
├─ INDEX.md
├─ INDEX_BY_KEYWORD.json
├─ INDEX_BY_IDENTITY.json
├─ INDEX_BY_STATUS.json
├─ INDEX_BY_RESOURCE.json
├─ INDEX_BY_TRIGGER.json
├─ INDEX_BY_RUNTIME.json
└─ IMPLEMENTATION_PROGRESS.json
```

즉 하나의 파일을 여러 가지 방법으로 찾을 수 있게 한다.

---

# 10. 예를 들어 “충전”을 찾는다면

충전과 관련된 자료가 여러 곳에 있을 수 있다.

```text
INDEX_BY_KEYWORD.json
```

에서:

```text
충전
↓
```

하면

```text
01_게임데이터/keywords/charge.json

01_게임데이터/identities/...
02_규칙/resource/charge.md
03_전투엔진/resource/charge_runtime.py
04_테스트/status/charge/...
```

를 한 번에 찾을 수 있게 한다.

---

# 11. “료슈의 대.박”을 찾는다면

인격 기준 검색:

```text
INDEX_BY_IDENTITY.json
```

→

```text
료슈
↓
1040603
↓
대.박
↓
관련 데이터
↓
관련 규칙
↓
관련 테스트
```

까지 연결한다.

이게 상당히 중요하다.

**한 파일을 찾는 것이 아니라 그 파일과 관련된 모든 자료를 찾을 수 있어야 한다.**

---

# 12. 파일 이름도 규칙을 고정한다

파일 이름은 가능하면:

```text
[대상]_[기능]_[종류]
```

형태로 통일한다.

예:

```text
charge_runtime.py
charge_rule.md
charge_test.py
charge_source.json
```

인격은:

```text
ryoshu.json
```

스킬은 데이터 안에서:

```text
identity_id
skill_id
coin_id
```

로 식별한다.

---

# 13. 모든 중요한 규칙에 ID를 붙인다

이게 나중에 굉장히 중요하다.

예:

```text
RULE-DMG-001
RULE-STATUS-BLEED-001
RULE-RESOURCE-CHARGE-001
RULE-TARGET-003
RULE-TRIGGER-012
```

그러면 계산 결과에서:

```text
피해 증가
→ RULE-DMG-001
```

처럼 연결할 수 있다.

그리고 이 ID를 검색하면:

> 이 규칙이 어디에서 사용되고 있는가?

를 바로 찾을 수 있다.

---

# 14. 파일을 찾는 기준은 5개로 한다

모든 주요 자료는 최소한 다음 기준으로 검색할 수 있게 한다.

```text
① 인격
② 스킬
③ 키워드/상태이상
④ 자원
⑤ Runtime/규칙
```

예를 들어:

> “충전을 사용하는 료슈 스킬 중 추가 공격이 있는 것”

이라면

```text
료슈
+
충전
+
추가 공격
```

으로 검색할 수 있어야 한다.

---

# 15. 가장 중요한 것은 “중복 저장”이 아니다

여기서 주의할 점이 있다.

검색하기 쉽다고 똑같은 데이터를 여러 파일에 복사하면 안 된다.

예를 들어 료슈의 충전 관련 스킬을:

```text
ryoshu.json
charge.json
additional_attack.json
```

에 전부 복사해서 넣는 것은 X.

실제 데이터는 한 곳에 두고:

```text
ryoshu.json
```

인덱스에서는:

```text
충전 → ryoshu.json의 해당 항목
추가 공격 → ryoshu.json의 해당 항목
```

처럼 **주소만 연결**한다.

즉:

> **원본은 한 곳, 검색 경로는 여러 개.**

## 핵심 원칙

**“파일을 잘게 나누는 것”이 목적이 아니다.**

목적은:

> **“어떤 규칙이나 인격을 찾고 싶을 때, 10초 안에 원본 → 규칙 → 코드 → 테스트까지 따라갈 수 있게 만드는 것.”**

그래서 최종적으로는

**원본 → 데이터 → 규칙 → 코드 → 테스트 → 검증**

이 한 줄로 연결되는 구조를 만드는 게 핵심이다.
