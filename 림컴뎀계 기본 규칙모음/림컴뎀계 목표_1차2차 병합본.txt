ㅇㅇ. 지금까지 진행하면서 확정된 변경사항까지 반영하면, **두 목표 문서를 병합하고 방금 정한 출혈 처리까지 포함한 통합 최종 목표**는 아래처럼 잡는 게 가장 적절함.

# 림버스 컴퍼니 1턴 데미지 계산기 — 통합 목표

## 1. 프로젝트의 핵심 목적

이 프로젝트는 **자동으로 전투를 플레이하거나 최대 딜을 찾아주는 시뮬레이터가 아니다.**

사용자가 직접 지정한:

* 인격
* 스킬
* 행동 순서
* 공격 대상
* 시작 전투 상태
* 필요한 경우 합/코인 결과

를 입력하면, 계산기가 해당 **1턴의 전투를 실제 전투 진행에 가깝게 순서대로 재현**한다.

그리고 그 과정에서 발생하는:

* 일반 피해
* 코인별 피해
* 합
* 출혈 및 기타 상태이상
* 버프/디버프
* 자원 변화
* 추가 공격
* 원호 공격
* 강제 발동 스킬
* 조건부 효과
* 킬 관련 효과
* 기타 트리거

를 모두 계산하고 기록한다.

최종적으로는 **"이 1턴에서 누가 어떤 스킬로 얼마의 피해를 냈는가?"뿐만 아니라 "왜 그 피해가 나왔는가?"까지 역추적할 수 있는 전투 분석기**를 목표로 한다.

---

# 2. 사용자가 지정한 행동을 기준으로 실행

사용자가 입력한 행동 순서가 기본 실행 순서다.

예:

```text
1. A 인격 S2
2. B 인격 S1
3. A 인격 S3
4. C 인격 S2
```

여기서 중요한 점은 **인격의 행동 횟수를 1회로 제한하지 않는 것**이다.

같은 인격이 여러 번 행동할 수 있으며,

* 사용자가 직접 여러 번 지정
* 패시브에 의한 추가 공격
* 원호 공격
* 강제 발동
* 재사용
* 기타 트리거

등으로 동일 인격의 행동이 여러 번 발생할 수 있다.

---

# 3. Requested Action / Resolved Action / Triggered Action 분리

행동은 최소한 세 단계로 구분한다.

```text
Requested Action
사용자가 지정한 행동
        ↓
Resolved Action
실제 조건/변환을 적용한 뒤 실행되는 행동
        ↓
Triggered Action
전투 중 새롭게 발생한 추가 행동
```

따라서 사용자가 입력한 스킬과 실제로 실행된 스킬이 달라질 수 있으며, 전투 중 발생한 추가 공격도 원래 행동과 구분해서 기록한다.

---

# 4. 전투 상태를 계속 갱신

각 행동뿐 아니라 **각 코인 단위로 전투 상태를 갱신**한다.

예를 들어:

```text
S3
 ├─ Coin 1
 │    ↓
 │   피해
 │    ↓
 │   적 Stagger 발생
 │
 ├─ Coin 2
 │    ↓
 │   변경된 Stagger 상태 적용
 │
 └─ Coin 3
      ↓
      변경된 상태 적용
```

따라서 한 스킬의 앞쪽 코인이 만들어낸 상태 변화가 뒤쪽 코인의 계산에 영향을 줄 수 있어야 한다.

추적 대상에는 필요에 따라:

* HP
* SP
* 공격 레벨
* 방어 레벨
* 공격력/방어력 관련 상태
* 자원
* 버프/디버프
* 상태이상 Potency/Count
* Stagger
* Resonance
* 탄약
* Charge
* Poise
* 각종 특수 자원
* 조건부 플래그

등이 포함된다.

---

# 5. Clash 처리

Clash는 1턴 계산에서 중요한 요소이므로 반드시 지원한다.

## 일반 계산 모드

일반적인 기본 계산에서는 **사용자가 지정한 아군이 모든 Clash에서 승리한다고 가정**한다.

예를 들어 적이 일반 코인 3개라면:

```text
1 Clash → 적 코인 3개
2 Clash → 적 코인 2개
3 Clash → 적 코인 1개
```

순서로 진행한다.

즉, Clash 결과에 따라 적의 활성 코인 수가 동적으로 감소하고, 그 결과 이후 계산도 바뀐다.

## 상세 확률 모드

필요한 경우:

```text
WIN
DRAW
LOSE
```

를 확률적으로 분기하고 각각의 상태를 별도로 추적한다.

이때 각 분기의 현재 적 코인, 아군 코인, HP, SP, 상태이상, 자원 등을 유지하면서 다음 Clash를 계산한다.

---

# 6. 출혈 계산 — 일반 모드와 상세 모드 분리

이 부분은 이번에 확정한 내용을 반영한다.

출혈은 **일반적인 상황에서는 모든 Clash를 승리한다고 가정하는 기본 계산**으로 처리한다.

### 예시

적이 일반 코인 3개이고 출혈 Count가 충분하다면:

```text
Clash 1
적 활성 코인 = 3
→ 출혈 3회
→ 적 코인 1개 제거

Clash 2
적 활성 코인 = 2
→ 출혈 2회
→ 적 코인 1개 제거

Clash 3
적 활성 코인 = 1
→ 출혈 1회
→ Clash 종료
```

따라서:

```text
3 + 2 + 1 = 6회
```

출혈이 발동한다.

예를 들어 출혈 Potency가 20이면:

```text
출혈 발동 횟수 = 6
출혈 피해 = 20 × 6 = 120
```

Count가 10이었다면:

```text
10 → 7 → 5 → 4
```

가 되어 최종 Count는 4다.

### 따라서 기본 출혈 계산은

```text
Enemy Active Coins
       ↓
3 → 2 → 1
       ↓
Bleed Proc
3 + 2 + 1
       ↓
총 6회
```

로 처리한다.

---

## 7. 파괴 불가 코인

파괴 불가 코인은 일반 코인과 별도로 관리한다.

최소한 내부적으로:

```text
enemy_normal_coins
enemy_unbreakable_coins
enemy_active_coins
unbreakable_coin_active
```

등을 구분한다.

따라서 **파괴 불가 코인을 단순히 일반 코인처럼 계속 차감해서 처리하면 안 된다.**

출혈 계산에서도 파괴 불가 코인과 일반 코인의 활성 상태를 구분하여 현재 발생해야 하는 출혈 이벤트를 계산한다.

---

# 8. 출혈 상세 옵션

출혈 상세 계산은 항상 사용하는 기능이 아니라 **출혈의 비중이 커졌을 때 더 자세하게 분석하기 위한 옵션**이다.

출혈 Potency가 낮을 때는 대표적인 계산으로 충분할 수 있지만, 출혈 Potency가 높아지면 전체 피해에서 출혈이 차지하는 비율이 커진다.

이때:

* 예상 출혈 발동 횟수
* 예상 출혈 피해
* Clash 결과별 출혈 발동
* Bleed Count 변화
* 최종 Count
* 확률 분포

등을 자세하게 확인할 수 있도록 한다.

필요한 경우 극단값을 제외한 **중앙 90% 범위**를 이용한 기대값 계산도 제공한다.

중요한 것은 이것이 **게임 내 RNG가 사라진다는 의미가 아니라 통계적인 분석 옵션**이라는 점이다.

---

# 9. 추가 공격 / 트리거 시스템

스킬 설명에 의해 전투 중 새로운 행동이 발생할 수 있다.

예:

```text
A S2
 ↓
조건 충족
 ↓
B 원호 공격
 ↓
B 공격
 ↓
추가 효과 발생
 ↓
C 추가 공격
```

이런 연쇄를 지원한다.

따라서:

```text
Requested Action
→ Trigger
→ Generated Action
→ Trigger
→ Generated Action
→ ...
```

형태의 재귀적인 트리거 구조를 사용한다.

다만 무한 재귀를 방지하기 위한 안전 제한은 필요하다.

---

# 10. 자원 시스템

자원은 특정 인격에 맞춰 하드코딩하기보다 범용 구조를 사용한다.

각 자원은 필요에 따라:

```text
현재값
최솟값
최댓값
증가량
감소량
소모량
조건
임계값
임계값 돌파
턴 종료
다음 턴 유지
```

등을 관리한다.

자원 변화 직후 조건을 평가하여 조건을 만족하면 관련 효과나 스킬을 발생시킨다.

---

# 11. 상태이상 / 버프 / 디버프

상태는 단순 ON/OFF만으로 처리하지 않는다.

필요하면:

```text
Potency
Count
Duration
Stack
Trigger Condition
Consume
Increase
Decrease
Next Turn Persistence
```

등을 관리한다.

특히 출혈처럼 **위력과 횟수가 서로 다른 의미를 가지는 상태**는 별도로 처리한다.

---

# 12. 대상 선택

단순히 `target_count = 1/2/3`만 보는 것을 넘어서 필요한 경우:

* 특정 대상
* HP가 가장 높은 대상
* HP가 가장 낮은 대상
* 특정 위치
* 특정 자원 수치가 높은 대상
* 좌/우 위치
* 명시된 target ID

등의 선택 조건을 처리한다.

향후 복잡한 다중 적 구조가 필요해질 경우 확장할 수 있도록 설계한다.

---

# 13. 로그 시스템 — 핵심 기능

이 부분은 **프로젝트의 중요한 축으로 확정**한다.

계산 결과만 보여주는 것이 아니라 **계산 과정을 전부 구조화해서 기록**한다.

## 기본 결과

```text
총 피해량
```

뿐만 아니라:

```text
인격별 피해량
스킬별 피해량
코인별 피해량
출혈 피해량
추가 공격 피해량
원호 공격 피해량
```

을 볼 수 있어야 한다.

예:

```text
총 피해량 : 12,450

A 인격
 ├─ S2 : 4,220
 │   ├─ Coin 1 : 1,230
 │   ├─ Coin 2 : 1,410
 │   └─ Coin 3 : 1,580
 │
 └─ S3 : 4,440

B 인격
 └─ S1 : 1,250

원호 공격
 └─ 1,420

출혈
 └─ 1,120
```

이렇게 **"어떤 인격의 어떤 스킬이 얼마나 딜을 했는가"를 바로 확인**할 수 있어야 한다.

---

# 14. 로그는 역추적 가능해야 함

더 자세히 보면:

```text
A S3
 └─ Coin 2
     ├─ 공격력
     ├─ 공격 레벨
     ├─ 스킬 위력
     ├─ 코인 위력
     ├─ 방어 레벨
     ├─ 내성
     ├─ 버프
     ├─ 디버프
     ├─ Stagger
     ├─ Critical
     └─ 최종 피해
```

까지 확인할 수 있도록 한다.

즉 로그의 목적은 단순히 "전투 기록"이 아니라:

> **실제 게임 결과와 계산기 결과가 다를 때 어느 단계에서 차이가 발생했는지를 찾는 것**

이다.

---

# 15. 로그 구조

내부적으로는 사람이 읽는 텍스트보다 **구조화된 로그를 원본 데이터**로 삼는 것이 좋다.

예:

```text
#001 ActionStart
#002 ClashStart
#003 ClashResult
#004 BleedProc
#005 CoinHit
#006 DamageCalculated
#007 StateChanged
#008 TriggerActivated
#009 GeneratedAction
...
```

각 이벤트에:

```text
event_id
action_id
identity_id
skill_id
source_action
trigger_source
event_type
before_state
event_data
after_state
state_delta
```

등을 기록한다.

그 위에서 사람이 보는 로그/리포트를 만들어낸다.

---

# 16. 실제 게임과 비교할 수 있는 구조

이 구조가 완성되면 실제 게임에서 측정한 결과와 계산기 결과를 비교할 수 있다.

예:

```text
실제 게임
A S3 = 4,812

계산기
A S3 = 4,650
```

그러면 로그를 통해:

```text
Coin 1
→ 일치

Coin 2
→ 불일치

Stagger 적용
→ 차이 발생

이후 피해
→ 연쇄적으로 불일치
```

처럼 **최초 차이점(first divergence)**을 찾아낼 수 있다.

이게 프로젝트의 정확도를 높이는 핵심 검증 방식이 된다.

---

# 17. Turn End / NextTurnState

1턴 계산은 **Turn End까지** 처리한다.

```text
START_STATE
 ↓
사용자 지정 행동
 ↓
추가 공격 / 트리거
 ↓
모든 상태 변화
 ↓
Turn End
 ↓
END_STATE
 ↓
NextTurnState
```

다음 턴을 자동으로 플레이하지 않는다.

다만 1턴에서 발생한:

* 다음 턴 효과
* 다음 턴 자원
* 다음 턴 스킬 변화
* 지속 상태

등은 `NextTurnState`에 저장한다.

이후 사용자가 그 상태를 다음 턴의 시작 상태로 넣어 직접 행동을 지정할 수 있다.

---

# 18. 최종 출력

최종 결과는 최소한 다음 구조를 가진다.

```text
INPUT
START_STATE

ACTION_TRACE
 ├─ Requested Action
 ├─ Resolved Action
 ├─ Triggered Action
 ├─ Clash
 ├─ Coin
 ├─ Damage
 ├─ Bleed
 └─ State Change

TOTAL DAMAGE

DAMAGE BY IDENTITY

DAMAGE BY SKILL

DAMAGE BY COIN

DAMAGE BY EFFECT

END_STATE

STATE_DIFF

NEXT_TURN_STATE

FULL EVENT LOG
```

---

# 최종적으로 우리가 만들려는 것

한 문장으로 정리하면:

> **사용자가 지정한 1턴의 전투를 실제 전투 순서와 상태 변화에 최대한 가깝게 재현하고, Clash·코인·출혈·자원·버프/디버프·추가 공격 등의 상호작용을 계산하며, 최종 피해뿐 아니라 인격별·스킬별·코인별 피해와 모든 중간 상태 변화를 로그로 기록하여 실제 게임 결과와 비교하고 계산 오류를 역추적할 수 있는 1턴 전투 분석기.**

그리고 이번에 확정한 출혈 규칙은 특히 중요하게 보면 됨.

**기본 모드에서는 `3 → 2 → 1 = 6회 출혈`을 바로 계산하고**, 출혈 비중이 높거나 사용자가 원할 때만 **Clash 확률 분기/기대값/중앙 90% 등의 상세 분석**으로 들어가는 구조.

이렇게 하면 계산기가 쓸데없이 모든 상황을 확률 시뮬레이션하는 것도 피하면서, **출혈이 실제 딜에서 중요해지는 상황에서는 충분히 깊게 분석할 수 있음.**
